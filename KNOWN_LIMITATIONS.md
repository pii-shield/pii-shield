# Known Limitations

PII-Shield is released and usable, but not yet fully production-hardened across all deployment modes. Production compliance deployments should account for the boundaries below.

## Kubernetes Logging

- The default file-based sidecar mode expects the application to write logs to the configured file path.
- Full transparent interception of standard Kubernetes `stdout`/`stderr` logs is not complete yet.
- Pipe mode is experimental and not recommended for production. It rewrites the target container command through `/bin/sh -c`, which can break distroless images (no shell), argument quoting, signal handling, and the app lifecycle. The webhook returns a warning when a pipe-mode policy is applied.

## Operator

- The Kubernetes operator is in stabilization. It supports policy objects and webhook injection, but advanced policy lifecycle management is still evolving.
- eBPF mode is experimental/R&D and should not be treated as production-ready interception.

## Scanner Configuration

- Set a persistent `PII_SALT` in production if deterministic hashes must remain stable across restarts.
- **Rotating `PII_SALT` breaks tag correlation, and there is no overlap mode.** The scanner holds one key and the tag carries no key id, so the same value gets a different tag before and after a rotation: joins and distinct counts across the boundary do not work. To trace a known identifier across periods, keep each retired salt with the dates it was active, run the identifier through the scanner under each one and search that period's logs for the tag it prints:

  ```bash
  echo 'iban=GB29NWBK60161331926819' | docker run -i --rm -e PII_SALT="$RETIRED_SALT" ghcr.io/pii-shield/pii-shield:2.2.4
  ```

  The tag depends only on the value and the salt, not on the key name around it, but the scanner has to redact the value in the first place: a short numeric account number is hidden only under a sensitive key, so pass the same `PII_SENSITIVE_KEYS` the deployment used. The tag is the first 3 bytes of HMAC-SHA256 (`pkg/scanner/scanner.go`), six hex characters, so in a large log a match is a candidate to confirm by time and surrounding fields, not proof. A retired salt still lets whoever holds it compute tags for its period, so keep it as a secret and destroy it when the logs of that period are deleted. Emitting old and new tags side by side during a transition is not built.
- Adaptive entropy thresholding is experimental and should be validated against representative log traffic before enabling.
- Custom regex and safe regex rules should be tested with real log samples to avoid false positives or false negatives.
- **The card detector only knows the major networks.** A digit run counts as a card when it passes Luhn and starts with a Visa, Mastercard, American Express, Discover, JCB, Diners Club or UnionPay issuer prefix at a length that issuer uses (the table is in `pkg/scanner/bin.go`). Maestro is left out on purpose — its range is wide enough to admit most numeric IDs — and store cards, fleet cards and regional schemes are not listed. Such a number may still be redacted by entropy, but it will not carry the `card` label; add a custom regex if a specific scheme matters to you.
- **A phone number is only found in three shapes.** With a leading `+`, in North American 3-3-4 punctuation, or as the value of a key whose last word names a phone (`phone`, `mobile`, `tel`, `msisdn`, `wa_id`, ...; the list is in `pkg/scanner/phone.go`). A number written as bare digits under any other key (`"from": "4917412345678"` in a WhatsApp webhook, `to=`, `caller=`) is indistinguishable from an order id or a millisecond timestamp and is not hidden; add a custom regex or a sensitive-key pattern for such keys. National formats other than North American (`020 7946 0958`, `0170 1234567`) are found only under a phone key. A `+` at the very start of a line is read as a diff marker, so a phone written first on a line keeps its `+` and is not recognised. A phone in a URL is hidden through the parameter loop, so it needs to be a whole parameter value (`?mobile=07700900123`), not part of one.
- **A rule can never match a phrase that spans two words.** Rules are applied in `processSingleToken` (`pkg/scanner/scanner.go`) to one whitespace-separated token at a time, so a pattern like `British Asian` is never tested against anything containing a space, however it is written — the scanner has already split the line before the rule is reached. Single-word patterns (`^Asian$`) work normally. This is a boundary of the design, not a gap in the rule list: matching phrases in the core would mean carrying multi-token state through the tokenizer, and free-text semantics is reserved for the selective PII model plan. Handle multi-word categories — GDPR Article 9 special-category phrases, for instance — before the text reaches the scanner.
- **A key that looks like a field name is not scored.** In `key=value` the key half is checked only when it does not have a field-name shape (`writeKeyHalf` in `pkg/scanner/scanner.go`). A key with `_`, `-`, `.`, `:`, `&`, `;` or `%` in it, one made only of letters with at most trailing digits (`requestId`, `HTTP`, `sha256`), or a strict camelCase name with a short number inside a word (`krb5KeyVersionNumber`, `s3BucketName`), is written out as is unless it matches a secret signature such as an AWS or GitHub key. Scoring every key would hide ordinary field names, since `context_id` and `request_id` sit right at the entropy threshold. So a random secret made only of letters, one containing `_` or `-`, or a short one that happens to have the camelCase-with-number shape (`ZfUj2Cwy`), still passes when it is used as a key, and keys before a colon (`"key": value`) are not scored at all. The one exception before a colon is an e-mail address at the end of the token (`user lena@example.com: login failed`, `{"lena@example.com": …}`), which is hidden by its shape; with a value glued after the colon (`git@github.com:org/repo.git`, `lena@example.com:hunter2`) the address is written out as before and only the value is scored.
- **A URL password cut by the tokenizer leaks its head.** The password in `scheme://user:password@host` is hidden whatever it contains, `/`, `?`, `#` and `@` included. But a line is split into tokens at spaces and at `,` `;` `(` `)` `[` `]` `{` `}` `<` `>` before the URL is read, and RFC 3986 allows `,` `;` `(` `)` unencoded in a password. In `postgres://u:Xk9p,Q2mZ@db/app` the URL ends at the comma, so `Xk9p` is written out and the rest is hidden as an ordinary token. Percent-encode such characters (`%2C`), as URL libraries do. Separately, a bracketed IPv6 host (`postgres://[::1]:5432/app`) splits the same way, and the port and path after it are hidden by entropy.
- **A compound of words is scored one word at a time.** A token joined by `-`, `.`, `_` or `/` whose parts are word-shaped and read like words (`gpt-4o-mini`, `search.max_results`, `AppleWebKit/537.36`) is scored as its most complex part, not as one string, so model names, setting keys and User-Agent components are no longer hidden. A camelCase name with a number inside a word (`s3BucketName`, `http2Enabled`) is scored the same way, part by part. Generated codes with equal groups (`abcd-efgh-ijkl-mnop`) and compounds that contain a sensitive word (`auth_…`, `api_key`) keep the whole-token score. The cost: a password made of words (`blue-Tiger-42`, `Welcome-123`) written bare in prose, with no key in front of it, is no longer caught, and neither is a short random tail behind an ordinary word (`session_Jcnagyqr`). The same goes for a dictionary word right after a bare sensitive word in prose (`password swordfish`): an all-letter word that reads as English is kept there, because `token expired` and `authentication failed` are what such lines say; a value with a digit or a symbol (`password hunter2`) and any value after `:` or `=` are still hidden. For the camelCase form the measured cost is small: of 20 000 random base62 tokens, 139 of 8 characters, 63 of 12 and 12 of 16 drop under the threshold, none of 24 or more. Under a sensitive key (`password=blue-Tiger-42`) both are still hidden.
- **A name/value pair is read left to right.** `{"name": "password", "value": "…"}` makes the value sensitive because the name comes first; the scanner reads a line once and does not go back. In `{"value": "…", "name": "password"}`, and in an OCPP 2.0.1 `SetVariables` frame that carries `attributeValue` before the variable name, the value is judged by its own score, so a word-like password passes (31 of 40 generated ones were hidden in that order, 40 of 40 with the name first).
- **A value named only by the words around it is judged by its own shape.** A key is one token, and it has to be a sensitive one. In `recovery code gyrpm-xjjxx rejected` the words `recovery code` are prose, and the short lowercase code scores under the threshold and passes (1 of 20 random codes of that shape). `recovery_code=…` and `"recoveryCode": …` are keys, but not sensitive ones by default; `PII_SENSITIVE_KEY_PATTERNS=recovery` makes them force their value. The prose form stays as it is.
- **A two-part code whose parts have the same length is hidden.** A compound such as `abcde-fghij` is taken for a generated code and scored whole, and that also catches vendor codes and model names of the same shape: `GAIA_RE01` (a Kintone error code), `ASUS_T00N` (a phone model). Limiting the rule to `-` and `/` freed them, but random upper-case codes joined by `_` started to pass (3 parts of 8 letters: 200 of 200 hidden before, 156 after), so the rule stays. Add the codes you need to `PII_SAFE_REGEX_LIST`.

## Roadmap Boundaries

Proxy-Wasm gateway integration, a visual Control Plane, and production-grade eBPF interception are planned R&D areas rather than completed stable features.
