# PII-Shield v3.0.0 Release Notes

PII-Shield v3.0.0 moves the rules out of the pod spec. A sidecar reads its rules from a policy file and picks up a change without a restart. The operator renders each `PiiPolicy` into that file and can pull it from a central HTTPS source. A new rule server keeps the rule sets of many clusters in one place, with a browser panel that previews a draft on the real scanner. Its publications can be signed with keys only the publishers hold, so a cluster accepts nothing else; every change goes to an activity log; an opt-in stats channel shows per cluster which rule version runs and what was hidden, as counters only; it runs on Postgres for several instances, and a deploy kit runs it on one machine with HTTPS and backups. Two dry runs let a team see what would be hidden before anything is: audit mode for the sidecar, and an eBPF audit agent that watches a pod's stdout and stderr without touching them. The scanner keeps the `Bearer` scheme word and hides short credentials and session tokens it let through before. The Go module path is now `github.com/pii-shield/pii-shield/v3`, and `injectionMode: ebpf` changed meaning; both are under Breaking Changes. A failed release gate now publishes nothing.

## Highlights

- **Rules without a restart (#326, #327).** `PII_CONFIG_FILE` points the sidecar at a JSON policy file, re-read when it changes. The operator writes every `PiiPolicy`'s rules into a ConfigMap and mounts it, so a policy edit reaches running pods in about a minute.
- **Central rules (#327).** `spec.remoteConfig` makes the operator pull a policy's rules from an HTTPS URL with a conditional GET, a token and an optional CA, and keep the last good version when a pull fails.
- **Rule server (#332, #334, #339).** One binary on SQLite or Postgres: rule sets per organization, immutable published versions, tokens for clusters, a browser panel with magic-link sign-in, a preview of a draft on pasted log lines, and an append-only activity log. Image `pii-shield-rules`, and a one-machine deploy kit (#339).
- **Signed rule files (#339).** A publisher signs a publication with an Ed25519 key that never reaches the server; `spec.remoteConfig.signature.publicKeys` makes the operator accept only files signed by those keys, for that set, never older than the last one.
- **Stats channel (#339).** `spec.stats`, off by default: the operator reads its sidecars' counters inside the cluster and sends one summary per interval. The rule server shows per cluster the pods, the rule revision they run, whether the cluster is behind, lines and hidden values by type.
- **Audit mode (#326, #327, #333).** `PII_MODE=audit`, or `auditMode: true` in a `PiiPolicy`, passes every line through unchanged and counts what would have been redacted.
- **eBPF audit agent (#326, #327, #329).** `injectionMode: ebpf` injects an agent that reads what a pod writes to stdout and stderr and counts what would have been redacted. It never changes the stream. Image `pii-shield-ebpf`.
- **Bearer and session tokens (#335).** `Authorization: Bearer abc123` keeps `Bearer` and hides the token; `Cookie: theme=dark; sid=abc123def` hides the session id.

## Features

### Policy file (#326)

`PII_CONFIG_FILE` names a JSON file in the format the SDKs pass to `init_config`: `entropy_threshold`, `confidence_score`, `min_secret_length`, `sensitive_keys`, `sensitive_key_patterns`, `custom_regexes`, `safe_regexes` and the other rule fields, plus an optional `revision` string. The sidecar checks the file's modification time and size every `PII_CONFIG_RELOAD_SECONDS` (default 10; `0` reads it once), so the kubelet's atomic ConfigMap update is seen as a change.

- **The environment wins.** A `PII_*` variable that is set is laid over the file on every load.
- **No salt from the file.** `salt` and `fail_policy` in the file are ignored with a warning; the salt chosen at start is kept across reloads, so markers stay comparable.
- **A bad file is rejected whole.** Invalid JSON, an invalid or empty pattern, or a value out of range keeps the previous rules in force and logs why.

With metrics on: `piishield_config_reloads_total`, `piishield_config_reload_errors_total`, `piishield_config_last_reload_timestamp_seconds`. The Go package exposes the same parsing as `scanner.ParsePolicyJSON`, `scanner.LoadPolicyFile` and `scanner.ApplyEnvOverrides`. See CONFIGURATION.md, section Policy File.

### Operator: a policy file per PiiPolicy and central rules (#327)

The controller renders the rule fields of every `PiiPolicy` into an owned ConfigMap `pii-shield-policy-<name>` (`policy.json`, no salt, `revision` set to the policy's generation). The webhook mounts it optional and read-only at `/etc/pii-shield` and sets `PII_CONFIG_FILE` on the sidecar in file and pipe modes.

`spec.remoteConfig` adds a central source:

- `url`: HTTPS only, unless `allowInsecure: true`.
- `intervalSeconds`: default 300, minimum 30; a failed pull is retried within 60 seconds.
- `headerSecretRef`: a Secret key holding the whole `Authorization` value. `caBundleSecretRef`: a CA bundle for a private server.
- `signature.publicKeys` (#339): accept only signed files; see Signed rule files below.

Each pull is a conditional GET (`If-None-Match`, 10 s timeout, 256 KiB limit). The file is validated whole as the sidecar does it. The policy's own rule fields are laid over it, and the result goes into the same ConfigMap. A failed pull keeps the last good rules, and `status.remote` says what happened. The operator chart's PrometheusRule gains alerts for stale and failing pulls.

### Rule server (#332, #334)

`rules-server` keeps organizations, rule sets, immutable versions and tokens in one SQLite file, or in Postgres (below). A cluster fetches `GET /v1/{org}/{set}/policy.json` with a Bearer token and gets an ETag and `304 Not Modified`; that URL is what `spec.remoteConfig` points at.

- **Versions.** Publishing creates a new version; a rollback publishes an older revision again, and the history is kept.
- **Validate and preview.** `POST …/validate` runs the checks of a publish without storing anything. `POST …/preview` runs up to 200 log lines through the real scanner with a draft or the published version and returns each line before and after.
- **Panel.** Embedded in the binary: rules editor, preview, versions with diff and rollback, tokens, a `PiiPolicy` snippet, members. Sign-in is a magic link mailed by SMTP, or written to the log when no mail server is set.
- **Image.** `pii-shield-rules`, distroless, non-root, `/data` for the SQLite file.
- **Activity log (#339).** Every change in an organization is an entry: who, what, which object, when, from which address, refused publications included; no secret is written, a token appears by its prefix. The database refuses to change or delete an entry. Pulls are not entries; each token shows its last pull time and address instead. Panel page Activity, `GET /api/orgs/{org}/audit`.
- **Watching it (#339).** Each token counts its pulls per day (new and unchanged files apart, 90 days), shown on the Tokens tab and at `GET …/pulls`; `--metrics-listen` serves Prometheus metrics on a separate address (`piishield_rules_requests_total`, `…_request_duration_seconds`, `…_policy_pulls_total`, `…_reports_received_total`); an access log line per request names the route, status and token prefix, never a token value (`RULES_ACCESS_LOG=false` turns it off).
- **Two kinds of token (#339).** A pull token (`psr_`) only reads a set's rules; a report token (`pss_`) only sends its stats reports.

`docs/rules-server.md` covers running it, the API, connecting a cluster, and a first-steps section for someone given a server's address. The first version's limits are under Known Limitations.

### Signed rule files (#339)

A publisher makes an Ed25519 key on the panel's Signing keys page, where the browser keeps it non-extractable, or with OpenSSL for a script; the server gets only the public half. Once an organization has a key, the server refuses an unsigned publication and checks every signature against the stored file before it publishes. What is signed is a short statement: the set, a publication number that grows with every publish (a rollback included), the revision, and the file's SHA-256. The server serves it at `GET /v1/{org}/{set}/policy.json.sig` under the pull token.

With `spec.remoteConfig.signature.publicKeys` the operator pulls the `.sig` next to the file and accepts the file only if one of the keys signed it, for the expected set (taken from the URL or `signature.set`), with a publication number not lower than the last accepted. Anything else keeps the last good copy, with a reason in `RemoteSynced` (`SignatureMissing`, `SignatureInvalid`, `SignatureUntrusted`, `SignatureReplayed`, `SignatureConfig`); `status.remote.publication` and `status.remote.signedBy` say what was accepted. A copy accepted before signatures were turned on, or signed by a key since removed, is not kept.

### Stats channel (#339)

`spec.stats` (`url`, `intervalSeconds` default 300 and minimum 60, `clusterName`, `headerSecretRef`, `caBundleSecretRef`, `allowInsecure`) turns it on for a policy. The webhook opens the sidecar's counters on port 9090, as audit mode does. Every 30 seconds the operator's leader lists the policy's injected pods and reads `/metrics` from each inside the cluster; it adds the growth since the last read, treats a lower value as a sidecar restart, and only starts counting a pod at its first read, so an operator restart never counts twice. Every interval it POSTs one `pii-shield-stats-v1` report: pods reporting, rule revisions running, the remote publication and signer, lines, errors, values hidden by type, and in audit mode what would have been hidden. Never a log line, a value or a hash. A failed post keeps the counts for the next one. `status.stats` shows the last report and error; `piishield_operator_stats_reports_total{result}` and `piishield_operator_stats_pods_reporting` are on the manager's metrics endpoint.

The rule server takes reports at `POST /v1/{org}/{set}/report` with a report token, keeps them 90 days, and shows them on a set's Clusters tab. Any receiver that accepts the JSON (documented in `operator/README.md`) works instead.

The sidecar gains `piishield_config_revision_info{revision}`, `1` for the revision of the policy file in force.

### Several instances and a deploy kit (#339)

`RULES_DB` (`--db`) takes a `postgres://` URL. Several server processes then share one database: rule sets, versions, publications, tokens, keys, the activity log, reports, sign-in links and sessions, so a link mailed by one instance signs in through another. Versions and publications of a set are numbered one after the other under a row lock even when two instances write at once. The log shows the URL with its password masked. SQLite stays the default for one process.

`deploy/rules-server` runs the server on one machine with Docker Compose: Caddy in front for HTTPS with a certificate it renews itself, Litestream copying the SQLite database to an S3-compatible bucket a few seconds behind every change, and a restore step that brings the database back on an empty disk. The README covers the first organization in invite mode, a restore drill, and upgrades.

### Audit mode (#326, #327, #333)

`PII_MODE=audit` is the sidecar's dry run. Every line goes through the scanner and is written out byte for byte as it came in; what would have been redacted is only counted:

- `piishield_audit_lines_total{result="clean"|"would_redact"}`;
- `piishield_audit_findings_total`, by detector type;
- `piishield_audit_mode`.

Both line series exist from the start, at zero, so an audit sidecar that sees nothing is visible. Audit mode never drops a line, whatever `PII_FAIL_POLICY` says.

`spec.auditMode: true` on a `PiiPolicy` sets `PII_MODE=audit` on the sidecar, turns its metrics on at port 9090 (`pii-metrics`) with an hourly log summary, and warns at admission that the logs are not redacted. `docs/production-adoption-checklist.md` now starts with step 0: two weeks in audit mode, read the counters, then switch to redaction with a rollout restart. The runbooks cover what to read.

### eBPF audit agent (#326, #327, #329)

A raw tracepoint on `sys_enter` copies what a pod's processes write to stdout and stderr (`write` and `writev`) to an agent that runs the scanner on it and exports the same audit counters, plus:

- `piishield_ebpf_events_total`;
- `piishield_ebpf_dropped_records`;
- `piishield_ebpf_attached`.

The program is CO-RE and needs a kernel of 5.8 or newer with BTF, `CAP_BPF` and `CAP_PERFMON`; it needs no hostPath and no privileged container. The operator injects it as a native sidecar with a startup probe on `/healthz`, which answers only once the program is attached, so the application starts after the agent can see it. If the program cannot be loaded, the agent fails open: it logs why, serves `/healthz` and reports `piishield_ebpf_attached 0`.

Redaction through eBPF is not possible in any supported way, because the kernel offers no production means for an eBPF program to rewrite what a process writes. The agent only observes. `docs/ebpf-audit.md` explains why, lists the requirements, and covers what the agent does not see and the node-level privilege it holds. Image `pii-shield-ebpf`, chart value `sidecar.ebpfImage`.

## Security

### Under-redaction fixed (#335)

Each of these passed in the clear on v2.3.1:

- **A short token after `Bearer`.** `Authorization: Bearer abc123` hid the word `Bearer` and kept `abc123`: the six-letter scheme word took the key's value slot, and the token after it was forced only from 16 characters. Now `Bearer`, `Digest` and `Negotiate` stay as words after an authorization key. The next token after `Bearer` is hidden at any length if it looks like a secret: at least `PII_MIN_SECRET_LENGTH` characters, a digit or a symbol, not a timestamp, not a scheme parameter.
- **`authorization=Bearer abc123`** came out whole; it is hidden the same way.
- **A token with a sensitive word inside.** In `Bearer test-token-1` the token was read as a key name. A credential after a scheme word is now always treated as a value.
- **A short session token under a session or cookie name.** `Cookie: sid=abc123def`, `JSESSIONID=8f3kd92ls0` and `session_id: …` passed when the value was too short for the entropy check. A value under `sid`, `session`, `session_id`, `jsessionid`, `phpsessid`, `sessid` or `cookie` is now hidden when it has the shape of a token: at least `PII_MIN_SECRET_LENGTH` characters, a letter, and a digit or a symbol. It must be one value, not a list. This applies to pairs, cookie headers, `name: value`, JSON and URL parameters.

These stay as they were: `Bearer token expired`, `WWW-Authenticate: Bearer realm="api"`, `session=default`, `cookie_consent=true`, `session_count=12`, short values such as `sid=a1b2`, and the other cookies in a header (`theme=dark`).

No secret, salt or token needs to be rotated because of this release.

## Breaking Changes

- **Go module path (#336).** The module is `github.com/pii-shield/pii-shield/v3`. Code that imports the scanner changes `…/v2/pkg/scanner` to `…/v3/pkg/scanner`. The package API is unchanged apart from the three additions above. Without this, Go would refuse the v3.0.0 tag.
- **`injectionMode: ebpf` (#327).** It used to inject a privileged container from `ghcr.io/pii-shield/pii-shield:v2.0.0-ebpf` with a shared process namespace. It now injects the eBPF audit agent, which only observes. A `PiiPolicy` with `injectionMode: ebpf` must also set `auditMode: true`, or the API server rejects it on create or update.

**Behaviour changes to be aware of:**

- **Every injected sidecar gets the policy file (#327).** In file and pipe modes, pods created after the upgrade carry an optional read-only volume at `/etc/pii-shield` and `PII_CONFIG_FILE`. The operator now creates and owns one ConfigMap per `PiiPolicy` and reads Secrets named by `remoteConfig`; the chart's RBAC grants both. The rules in force do not change: the file holds the same fields the policy already set as variables, and the variables still win. Running pods keep their spec until they restart.
- **`Bearer` is kept as a word** after an authorization key, where v2.3.1 hid it. More short credentials and session tokens are hidden (see Security).
- **New metrics** on the sidecar: the reload counters, `piishield_config_revision_info` and the audit series above.
- **Values hidden for their key count as `key` (#340).** `piishield_redaction_events_total{type}` and `piishield_audit_findings_total{type}` gain the value `key` for a value hidden because of where it sits: under a sensitive key (`sensitive_keys`, `sensitive_key_patterns`, the built-in list), after `Basic` or `Bearer`, or as a URL password. Up to 2.3.1 these were counted as `entropy`, so dashboards and alerts on `type="entropy"` see a drop and a new `type="key"` series. The hourly summary line gains a `sensitive-key values` field. What is hidden, the markers and the hashes do not change.
- **The controller reconciles on spec changes only (#339).** A write to a policy's status no longer starts another reconcile, and with it another pull of `remoteConfig`; the pulls run on their interval as before.
- **The operator lists pods (#339).** It is used only for policies with `spec.stats`; the chart's RBAC grants `list` on pods.

## Kubernetes / Helm Changes

- CRD `PiiPolicy`: new fields `spec.remoteConfig` (with `signature`), `spec.auditMode` and `spec.stats`, and `status.remote` (with `publication` and `signedBy`) and `status.stats`; a validation rule ties `injectionMode: ebpf` to `auditMode: true`. `helm upgrade` installs the new CRD when `installCRDs` is on (the default).
- Operator chart: RBAC for ConfigMaps, for reading Secrets, and for listing pods. A new value `sidecar.ebpfImage` (repository `ghcr.io/pii-shield/pii-shield-ebpf`, tag defaults to the chart's app version). PrometheusRule alerts for stale and failing remote pulls, audit sidecars that would redact, and audit sidecars that see no lines.
- The standalone `pii-shield` chart is unchanged apart from its version.

## SDK Changes

`@aragossa/pii-shield-wasi` 3.0.0 (npm) and `pii-shield-wasi` 3.0.0 (PyPI) ship the rebuilt WASM kernel with the scanner fixes of #335. No API changes. The SDKs' `init_config` JSON is the policy file's format; a `revision` field in it is ignored.

## Known Limitations

Added or updated in KNOWN_LIMITATIONS.md:

- Audit mode is a dry run of the scanner, not of the deployment. In pipe and stdin modes the sidecar still sits in the stream's path; only file mode keeps it off the application's path. The counters say that a line would have changed and which detector fired, not which value.
- `auditMode` turns the sidecar's metrics on at port 9090. A pod that already uses that port has no counters, and nothing scrapes the port unless the cluster is told to.
- eBPF is observation only, needs a kernel of 5.8 or newer with BTF, and holds node-level privilege through `CAP_BPF` and `CAP_PERFMON`. Neither the `restricted` nor the `baseline` Pod Security Standard admits it. eBPF redaction is not planned.
- The rule server is a first version:
  - sign-in by magic link only;
  - rate limits kept in each process's memory, so several instances allow that many times the limit;
  - a signature stops a server that is taken over from handing out rules nobody signed, not from withholding a newer publication or going silent; the panel that signs in the browser comes from the same server;
  - the stats channel carries counters only, needs the operator to reach the pods on port 9090, misses a pod that lives less than 30 seconds, and alerts nobody.

## CI and Release

- **A failed release publishes nothing (#323, #324).** The Docker images and the SDKs are published from `release.yml` after GoReleaser has created the GitHub release, instead of from two workflows of their own. v2.3.0 shipped packages while its GitHub release failed; that cannot happen again.
- The release workflow builds and smokes the `pii-shield-ebpf` and `pii-shield-rules` images and publishes them with the others (#329, #332).
- CI loads the eBPF program into the runner's kernel and smokes the agent and its image; the rule server image is smoked end to end, from publishing a set to fetching it with a token (#326, #329, #332).
- The Performance Check report is posted as a comment on the pull request, forks included (#330).
- CI runs the rule server's store and server tests a second time on Postgres 16 (#339).

## Upgrade Notes

```bash
helm repo update
helm upgrade pii-shield-operator pii-shield/pii-shield-operator --version 3.0.0
helm upgrade pii-shield pii-shield/pii-shield --version 3.0.0
```

After the operator upgrade, restart the workloads whose sidecars should read the policy file (`kubectl rollout restart`); until then they run as before. If a `PiiPolicy` uses `injectionMode: ebpf`, add `auditMode: true` before you edit it. To try audit mode first, set `auditMode: true` on a policy, restart its workloads, and read `piishield_audit_lines_total` for a while before turning it off. To turn on the stats channel, add `spec.stats` and restart the policy's workloads once, so their sidecars open the counters.

Rollback: `helm rollback` the operator to 2.3.1. The ConfigMaps it created are left behind and are harmless; pods restarted under 2.3.1 lose the mount and the variable.

```bash
npm install @aragossa/pii-shield-wasi@3.0.0   # Node
pip install --upgrade pii-shield-wasi==3.0.0  # Python
go get github.com/pii-shield/pii-shield/v3/pkg/scanner@v3.0.0  # Go
```
